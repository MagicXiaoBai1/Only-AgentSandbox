# 测试计划：oas-driver Shim + 自动沙箱恢复

> 实现说明见 `0docs/实现说明-当前状态.md`。本文设计并给出可执行的测试方案。
> 核心问题"能不能单独只测 shim？"——**能**，见 §2。

## 0. 测试分层

| 层 | 目标 | 依赖 | 现状 |
|---|---|---|---|
| L1 单元/集成 | manager FSM、IPAM、store 幂等（mock 后端，不起真 VM） | 无 root、无 firecracker | ✅ 全绿（`cargo test`） |
| **L2 shim 单独** | **shim 启动 VM + snapshot 恢复链路**（绕过 runtime） | root + firecracker/jailer + 烘焙好的 bundle | ⬜ 待真机跑（脚本已就绪） |
| L3 runtime 端到端 | crictl/kubelet 走完整 RunPodSandbox → SSH | root + bundle + kubelet/crictl | ⬜ 待真机跑 |
| L4 韧性 | runtime 重启再发现 / shim 崩溃 re-attach / 应急杀 | L3 环境 | ⬜ 待真机跑 |

L2 是本计划的重点：它把"snapshot 恢复"这条最核心、最容易出问题的链路单独拎出来，不经过 CRI/manager，最快定位 shim/jailer/firecracker 的问题。

## 1. 前置：烘焙 bundle

所有 L2/L3 都依赖一个 net-enabled bundle（含 virtio-net `net1→tap0`）。

```bash
sudo ./tools/bake_bundle.sh base-1 2 1024
# 产出 /var/lib/oas/artifacts/snapshots/base-1/{vmlinux,rootfs.ext4,vmstate,mem}
```

烘焙脚本复用 `experiments/snap_double_shot` 已验证的 create 侧流程，并额外 `PUT /network-interfaces/net1`
（`iface_id=net1`、`host_dev_name=tap0`、固定 `guest_mac`）。镜像侧须已配 eth0 静态 IP `172.16.0.2/30`
+ sshd（非代码范围）。

> 烘焙只需做一次；bundle 是只读模板，可重复 restore 出多个 VM。

## 2. L2：shim 单独测试（核心）

### 2.1 能不能单独测 shim？

**能。** shim 是一个独立的 ttrpc server 进程，`Create` RPC 触发恢复。我们用一个小客户端
[`crates/oas-driver/examples/shim_smoke.rs`](../only-agent-sandbox/crates/oas-driver/examples/shim_smoke.rs)
直连 shim socket 驱动 `Create`/`State`/`Stop`，完全绕过 runtime/CRI/manager。这样：
- 排除 manager/net/storage 的干扰，**只**验证 shim + jailer + firecracker 恢复链路。
- 失败时日志集中在一个 shim 进程，定位快。
- 不需要 kubelet/crictl，只要 root + firecracker + bundle。

### 2.2 测什么

| 用例 | 操作 | 期望 |
|---|---|---|
| T1 恢复成功 | prep netns+tap0+rw → 起 shim → `shim_smoke create` | `state=Running`，firecracker 进程出现 |
| T2 状态查询 | `shim_smoke state` | `Running` |
| T3 SSH 可达 | `ip netns exec oas-<sid> ssh 172.16.0.2` | `SSH_OK`（镜像 sshd 就绪时） |
| T4 幂等 re-create | 再次 `shim_smoke create`（同 sid） | `state=Running`，不产生第二个 firecracker（re-attach） |
| T5 停止 | `shim_smoke stop` | shim 退出，firecracker 被杀，jail root/socket 清掉 |
| T6 re-attach | 恢复后**杀 shim**（留 firecracker）→ 重起 shim → `create` | re-attach 已存活 firecracker，`Running`，SSH 仍通 |

### 2.3 怎么跑

一条命令（脚本替你做 netns/tap/rw/起 shim/驱动/验证/清理）：

```bash
cd only-agent-sandbox

# 1. 清理我们测试遗留的 firecracker（按 sid 前缀，不会动 bake-base-1 / vm-a / vm-b / agent-rt 那些）
sudo pkill -f 'firecracker --id (smoke-|probe-)' || true

# 2. 正式重跑（不加 TEST_KEEP，让它走完整验证 + 清理）
sudo ./tools/test_shim.sh base-1 # 跑完自动 stop + 清理

sudo TEST_KEEP=1 ./tools/test_shim.sh base-1    # 保留现场，便于手动 SSH / 调试
```

脚本流程（[`tools/test_shim.sh`](../only-agent-sandbox/tools/test_shim.sh)）：
1. 建 netns `oas-<sid>` + tap0 + 网关 `172.16.0.1/30`（镜像 `oas-net::setup`）。
2. `truncate -s 1G` + `mkfs.ext4 -F` 制备 per-VM rw ext4（镜像 `oas-storage::provision`）。
3. `setsid oas-runtime shim --config ... --sandbox-id <sid> --socket <uds> --log-file <f>` 后台起 shim。
4. 等 shim socket 出现。
5. `shim_smoke create <sock> <cfg> <sid> <bundle_dir> <rw>` 触发恢复。
6. 验证：`pgrep firecracker` + `shim_smoke state`=Running + `ip netns exec ... ssh`。
7. 默认 `shim_smoke stop` + 清理；`TEST_KEEP=1` 保留。

手动驱动（不用脚本）：

```bash


# 终端 A：起 shim
sudo ./target/debug/oas-runtime shim \
  --config /etc/oas/config.toml --sandbox-id t1 \
  --socket /run/oas/oas-shim-t1.sock --log-file /var/log/oas/oas-shim-t1.log

# 终端 B：prep + 驱动（需先建 netns/tap0/rw，参考脚本 step 1-2）
sudo ./target/debug/examples/shim_smoke create /run/oas/oas-shim-t1.sock /etc/oas/config.toml t1 /var/lib/oas/artifacts/snapshots/base-1 /var/lib/oas/rw/t1.ext4
sudo ./target/debug/examples/shim_smoke state  /run/oas/oas-shim-t1.sock t1
sudo ./target/debug/examples/shim_smoke stop   /run/oas/oas-shim-t1.sock t1
```

### 2.4 通过判据

- T1/T2：`create` 返回 `state=Running` 且 `pgrep firecracker` 命中。
- T4：第二次 `create` 后 firecracker 进程数不变（=1），证明幂等 re-attach。
- T6：杀 shim 后 firecracker 仍在；重起 shim + `create` 后 `state=Running` 且 SSH 仍通（同一 firecracker）。
- 任一失败：看 `/var/log/oas/oas-shim-<sid>.log` + `$SANDBOX_DIR/root/fc.log`（firecracker 自身日志）。

### 2.5 常见失败排查

| 现象 | 可能原因 |
|---|---|
| `create -> state=Failed error=...jailer exited...` | jailer 权限/路径；看 shim.log 里 jailer stderr |
| socket 等待超时 | shim 启动崩溃；看 shim.log |
| firecracker 起来但 snapshot/load 失败 | bundle 不完整 / 权限；看 `fc.log` |
| SSH 不通（恢复成功） | 镜像 sshd/静态 IP/密钥；非恢复链路问题（T1/T2 仍算通过） |
| `find_fc_pid` 找不到 firecracker | comm 不是 `firecracker`（firecracker 二进制名异常）；检查 `/proc/*/comm` |

## 3. L3：runtime 端到端

L2 通过后，接上 runtime + CRI。

复用联调报告 §5 验证通过的 standalone kubelet + 静态 Pod 流程（仅把 type 从 0 换成 1、接真 bundle）：

```bash
# 1) 编译
cd only-agent-sandbox && cargo build --workspace

# 2) 烘焙 bundle（见 §1，仅一次）
sudo ./tools/bake_bundle.sh base-1 2 1024

# 3) 起运行时（root，UDS /run/oas.sock）
sudo OAS_SOCKET=/run/oas.sock ./target/debug/oas-runtime --config /etc/oas/config.toml &

# 4) 起 standalone kubelet（已避让端口 15250/15248，不连 api-server）
cd ../tests && bash start-kubelet.sh

# 5) 投放静态 Pod（image=img-b, type=1, 资源在 type1 预算内）
cat > agent-rt-test/static-pods/oas-test.yaml <<'YAML'
apiVersion: v1
kind: Pod
metadata:
  name: oas-kubelet-test1
  namespace: default
  annotations:
    agent-sandbox/type: "1"
spec:
  restartPolicy: Always
  containers:
    - name: workload
      image: img-b
      imagePullPolicy: IfNotPresent
      command: ["sleep", "infinity"]
      resources:
        requests: { cpu: "0.5", memory: "128Mi" }
        limits:   { cpu: "0.5", memory: "256Mi" }
YAML

# 6) 观察
crictl --runtime-endpoint unix:///run/oas.sock pods
crictl --runtime-endpoint unix:///run/oas.sock ps
pgrep -a firecracker
SID=$(crictl --runtime-endpoint unix:///run/oas.sock pods --name oas-kubelet-test1 -q)
sudo ip netns exec oas-$SID ssh 172.16.0.2
tail -f agent-rt-test/logs/kubelet.log
```

清理（按顺序：先停 reconcile，再停 runtime，最后收孤儿 firecracker + 清状态）：

```bash
WORK=/home/yunfei/Code/Only-AgentSandbox/tests/agent-rt-test

# 1) 删静态 Pod yaml + 停 standalone kubelet（用 pidfile，勿 pkill -x kubelet——会误杀宿主真 kubelet）
rm -f "$WORK/static-pods/oas-test.yaml"
kill "$(cat "$WORK/kubelet.pid" 2>/dev/null)" 2>/dev/null || true

# 2) 停 runtime（连带 shim 进程，comm 同为 oas-runtime）
pkill -x oas-runtime 2>/dev/null || true

# 3) 杀孤儿 firecracker（runtime/shim 死后残留，按 sid 前缀 sb- 清，不动 bake-/smoke-/probe-）
pkill -f 'firecracker --id sb-' 2>/dev/null || true

# 4) 清 jail root / netns / rw / 持久化 store（路径随 chroot_base_dir，此处为当前 /home/yunfei/oas-test）
sudo rm -rf /home/yunfei/oas-test/firecracker/sb-*
for ns in $(ip netns list | awk '/^oas-sb-/{print $1}'); do sudo ip netns del "$ns"; done
sudo rm -f /var/lib/oas/rw/sb-*.ext4 /var/lib/oas/store.redb
```

> 不清干净会埋雷：上一次失败遗留的 jail root / 孤儿 firecracker 会让下次 create 行为异常（如 `find_fc_pid` 误判、socket 占用），且 `pkill -x kubelet` 在真 k8s 节点上会连宿主 kubelet 一起杀。

静态 Pod 须带 annotation `agent-sandbox/type: "1"`（CRI convert 解析为 `type_id`），镜像名命中
type 1 白名单（`img-b`）。可改 `Config` 的 `image_whitelist` 适配实际镜像。

通过判据：`crictl pods` READY + firecracker 进程 + SSH 通 + kubelet 事件 Created/Started 无 CRI 错误。

## 4. L4：韧性

| 用例 | 操作 | 期望 |
|---|---|---|
| R1 runtime 重启再发现 | L3 起一个 pod → kill runtime → 重起 runtime → `crictl pods` | pod 仍 READY；shim+firecracker 全程未死 |
| R2 shim 崩溃自愈 | L3 起一个 pod → kill shim（不动 firecracker）→ `crictl inspectp` 触发 `get_vm` | runtime re-spawn shim re-attach；VM 仍活、SSH 仍通 |
| R3 应急杀 | L3 起一个 pod → kill shim → `crictl stopp <pod>` | runtime 应急杀 firecracker（过 mntns 校验）；jail root/socket 清；无残留 firecracker |
| R4 幂等 runp | 同 pod_uid 重复 `crictl runp` | 返回同一 sandbox_id，不产生第二个 VM |

R1 验证"runtime 重启不影响 shim"这一头号需求；R3 验证应急杀路径 + 防杀错进程。
