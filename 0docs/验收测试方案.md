
# kubelet 测试方案  

> 下面是基于 `standalone kubelet` 的 MVP 三测完整方案。先讲顶层设计和 *“为什么这么测才正确”*，再给可直接落地的文件与命令。三个测试共用同一套环境脚手架，只是观测点和判据不同。

---

## 一、顶层设计

### 1.1 测试分层与各自的证明目标

| 测试 | 证明什么命题 | 观测边界 | 不证明什么 |
|------|--------------|----------|------------|
| **T1 基础 (happy path)** | runtime 的 CRI 生命周期正确：kubelet 能把一个 Pod 从无 → Running → 彻底删除无残留 | CRI 调用链 + Firecracker 进程 + 宿主机残留 | 沙箱内是否可用、性能 |
| **T2 可用性** | 沙箱“活着且能对外通信”：出站到外部 IP 通、能建 SSH 会话并执行命令拿回显 | 沙箱 guest 内部 → 外部 IP | 隧道鉴权、注册中心（已划出 runtime 边界） |
| **T3 性能/压力** | runtime 的两个核心 KPI：• 单 VM 冷启动耗时、单机并发密度上限与稳定性 | 时间戳采样 + 批量并发 + 资源水位 | 多节点调度（归 scheduler） |

---

### 1.2 为什么“用 standalone kubelet”而不是 `crictl` 或全集群，是正确的测试载体

- **比 `crictl` 强**：`standalone kubelet` 跑真实的 `syncLoop + PLEG`，每秒 relist，会自动驱动 `Run→Create→Start→Stop→Remove`，并持续轮询 `*Status`。这能验证真实 kubelet 的隐性契约（metadata 匹配、状态机、就绪/驱逐），而 `crictl` 手动单测做不到。
- **比全集群轻且更聚焦**：你这三个命题的瓶颈全部发生在单节点内部——CRI 正确性、沙箱出站、单机密度，都与 `scheduler/api-server` 无关。引入全集群只会把“调度 bug”和“runtime bug”混在一起，增加定位成本。把多节点调度、隧道鉴权排除在外，是前面已达成的职责边界共识。
- **触发方式确定**：往 `--pod-manifest-path` 目录丢/删 YAML 即触发创建/销毁，无需 `api-server`，可脚本化、可复现。

---

### 1.3 三个“正确性”前提（否则测试结论不成立）

1. **观测独立于被测对象**：判据不能只看 runtime 自己打的日志（它可能撒谎）。每个命题都用第二来源交叉验证——  
   - CRI 状态用 `crictl` / VM 真实存在用宿主机 `ps` / Firecracker API  
   - 网络用沙箱内部实际发包  
   - 残留用宿主机文件系统/网络设备清点。

2. **happy path 必须包含销毁闭环**：只测“起来了”会放过资源泄漏；T1 的判据延伸到“删除后宿主机干净”。

3. **性能测试必须制造并发**：`standalone` 默认串行下发；T3 要主动并发投放，否则测不出锁争用、VMM 创建风暴、IP/fd 耗尽这些只在密度下出现的真问题。

---

### 1.4 拓扑

```text
1  宿主机（裸机 / 支持 KVM 的 VM, /dev/kvm 可用）
2  ├─ 你的 CRI runtime          监听 unix:///var/run/agent-runtime.sock
3  │─ standalone kubelet        --pod-manifest-path=$WORK/static-pods
4  │                             --container-runtime-endpoint=指向上面 socket
5  │─ crictl                    指向同一 socket（观测用）
6  └─ mock 注册中心/外部靶机    一个固定 IP，跑 sshd（T2 的对端）
7
```

## 二、共用脚手架文件

约定工作目录：`WORK=$HOME/agent-rt-test`。下面文件一次建好，三测共用。

### 2.1 环境变量与目录 `env.sh`

```bash
#!/usr/bin/env bash
# env.sh —— 所有测试 source 此文件

export WORK="$HOME/agent-rt-test"
export RT_SOCK="unix:///var/run/agent-runtime.sock"      # standalone kubelet 监听目录
export MANIFEST_DIR="$WORK/static-pods"                   # 待投放的 yaml 模板池（不被 kubelet 监听）
export POOL_DIR="$WORK/pod-pool"                          # pod-pool/ 下的模板拷贝至此
export LOG_DIR="$WORK/logs"
export RESULT_DIR="$WORK/results"
export EXT_TARGET_IP="10.0.0.250"                         # T2 外部靶机 IP（改为你自己的）
export EXT_TARGET_DOMAIN="registry.test.local"            # 固定域名（DNS 验证用）
export CRITCL="--runtime-endpoint $RT_SOCK --image-endpoint $RT_SOCK"
mkdir -p "$MANIFEST_DIR" "$POOL_DIR" "$LOG_DIR" "$RESULT_DIR"
```

### 2.2 `crictl` 配置 `/etc/crictl.yaml`

```yaml
runtime-endpoint: unix:///var/run/agent-runtime.sock
image-endpoint: unix:///var/run/agent-runtime.sock
timeout: 20
debug: false
```

### 2.3 `standalone kubelet` 启动脚本 `start-kubelet.sh`

```bash
#!/usr/bin/env bash
source "$(dirname "$0")/env.sh"

# 仅本地静态 Pod 模式，不连 api-server
kubelet \
  --container-runtime-endpoint="$SRT_SOCK" \
  --image-service-endpoint="$SRT_SOCK" \
  --pod-manifest-path="$MANIFEST_DIR" \
  --root-dir="$WORK/kubelet-root" \
  --fail-swap-on=false \
  --cgroup-driver=systemd \
  --runtime-request-timeout=30s \
  -v=4 \
  > "$LOG_DIR/kubelet.log" 2>&1 &
echo $! > "$WORK/kubelet.pid"
echo "kubelet started, pid=$(cat $WORK/kubelet.pid), log=$LOG_DIR/kubelet.log"
```

> 💡 注：`-v=4` 让 kubelet 把 PLEG relist、sandbox 重建、eviction 这些关键事件打到日志，T1 抓“无限重建”靠它。

## 三、T1 基础测试 —— 生命周期 happy path

### 3.1 命题与判据

**命题**：对每种沙箱，kubelet 能把它从 `无 → Running → 彻底删除`，且全程无异常弥合、删除后宿主机无残留。

| 阶段       | 判据（全部第二来源交叉验证） |
|------------|------------------------------|
| **创建**   | `crictl pods` 出现该 sandbox 且 `State=SANDBOX_READY`；`crictl ps` 容器 `State=CONTAINER_RUNNING` |
| **VM 真存在** | 宿主机 `ps` 能看到对应 firecracker 进程，数量与沙箱数一致 |
| **稳态**   | 持续 ≥30s，Pod 不发生重建：kubelet 日志无 `Killing / SyncLoop ... recreate`；`RunPodSandbox; sandbox_id` 不变 |
| **无误驱逐** | kubelet 日志无 `eviction / DiskPressure` 事件 |
| **删除**   | 移除 manifest 后 `crictl pods` 不再出现；firecracker 进程消失 |
| **无残留** | TAP/veth 设备清空、IP 归还、临时块设备 detach、工作目录无残留 |

---

### 3.2 测试脚本 `t1_happy_path.sh`

```bash
#!/usr/bin/env bash
set -uo pipefail
source "$(dirname "$0")/env.sh"
TYPES=("lite" "pro" "browser")
PASS=0; FAIL=0

log() { echo "[$(date +%T)] $*"; }

snapshot_residue() {
  # 记录基线：进程数、网络设备、IP
  echo "fc_procs=$(pgrep -c firecracker 2>/dev/null || echo 0)"
  echo "taps=$(ip -o link show type tun 2>/dev/null | wc -l)"
}

for t in "${TYPES[@]}"; do
  log "=== T1 [$t] start ==="
  BASE=$(snapshot_residue)

  # 1) 投放
  sed "s/__ID__/$t/" "$POOL_DIR/$t.yaml" > "$MANIFEST_DIR/$t.yaml"

  # 2) 等待 Running (最多 30s)
  ok=0
  for i in $(seq 1 30); do
    if $CRITCL pods --name "sb-$t-t1" -q 2>/dev/null | grep -q .; then
      pid=$($CRITCL pods --name "sb-$t-t1" -q | head -1)
      st=$($CRITCL inspectp "$pid" 2>/dev/null | grep -o 'SANDBOX_READY' | head -1)
      if [[ "$st" == "SANDBOX_READY" ]] && (( ok=1 )); break; fi
    fi
    sleep 1
  done
  [[ $ok -eq 1 ]] && log "[$t] sandbox READY" || { log "[equation]t FAIL: not ready"; FAIL=$((FAIL+1)); continue; }

  # 3) 校验 firecracker 进程确实多了一个
  pgrep -a firecracker | grep -q "$t" && log "[$t] firecracker process present" \
    || { log "[equation]t FAIL: no fc process"; FAIL=$((FAIL+1)); continue; }

  # 4) 稳态 30s，抓重建/驱逐
  sid_before=$(grep -ci "evict\|DiskPressure" "$LOG_DIR/kubelet.log")
  recreate=$(grep -c "RunPodSandbox.*sb-$t-t1" "$LOG_DIR/kubelet.log")
  sleep 30
  sid_after=$(grep -ci "evict\|DiskPressure" "$LOG_DIR/kubelet.log")
  if [[ "$sid_before" == "$sid_after" ]] && [[ "$recreate" -eq 0 ]]; then
    log "[$t] stable 30s, sandbox_id unchanged, no eviction"
  else
    log "[equation]t FAIL: unstable (recreate or eviction)"; FAIL=$((FAIL+1)); continue
  fi

  # 5) 删除
  rm -f "$MANIFEST_DIR/$t.yaml"
  gone=0
  for i in $(seq 1 20); do
    $CRITCL pods --name "sb-$t-t1" -q | grep -q . || { gone=1; break; }
    sleep 1
  done
  [[ $gone -eq 1 ]] && log "[$t] removed from CRI" || { log "[equation]t FAIL: not removed"; FAIL=$((FAIL+1)); continue; }

  # 6) 残留检测：对比基线
  AFTER=$(snapshot_residue)
  if [[ "$BASE" == "$AFTER" ]]; then
    log "[$t] residue: no residue, PASS"; PASS=$((PASS+1))
  else
    log "[$t] FAIL: residue detected"; FAIL=$((FAIL+1))
  fi
done

log "T1 RESULT: PASS=$PASS FAIL=$FAIL"
exit $FAIL
```

### 3.3 为什么这样测是对的

- ✅ 用 `crictl`（独立于 runtime）确认 CRI 状态机、宿主机 `ps` 确认 VM 真实存在（防 runtime 撒谎）。
- ✅ 30s 稳态窗口专门覆盖 PLEG 每秒 relist —— metadata/状态错误会在该窗口表现为 `sandbox_id` 变更或重建日志。
- ✅ 残留检查把 happy path 闭环，这是高可靠必须满足的硬性要求。

## 四、T2 可用性测试 —— 出站可达 + SSH 可执行

### 4.1 命题与判据

**命题**：沙箱启动后，从 guest 内部能解析固定域名、ping 外部靶机 IP、并对靶机建立 SSH 会话执行命令拿到回显。

> **关键正确性**：验证必须在沙箱内部发起（出站方向），而不是宿主机 ping 沙箱（入站）。因为你的产品模型是沙箱主动出站连注册中心。standalone 下无带外隧道，用 `"沙箱→外部靶机"` 直接代理这条出站链路即可证明 runtime 的网络责任成立；隧道鉴权不在本测范围。

| 检查         | 方法                                                                 | 判据                     |
|--------------|----------------------------------------------------------------------|--------------------------|
| 沙箱有 IP/路由 | `guest 内 ip addr / ip route`                                        | 有非 lo 的 IP + 默认路由 |
| DNS 解析      | `guest 内 nslookup $EXT_TARGET_DOMAIN`                              | 能解析                   |
| 出站连通      | `guest 内 ping -c3 $EXT_TARGET_IP`                                  | 丢包率 0（或可接受）     |
| 长连接        | `guest 内对靶机 nc -z 或保持 TCP`                                   | 建连成功                 |
| SSH 执行      | ```bash<br>guest 内 ssh user@$EXT_TARGET_IP 'echo SANDBOX_OK'<br>``` | 回显含 `SANDBOX_OK`      |

---

### 4.2 "从 guest 内部执行命令" 的通道问题（重要）

你已确认 `Exec / ExecSync` 不经 CRI 实现（走带外隧道），所以 standalone 下没有 `crictl exec` 可用。T2 阶段用下面任一方式把命令送进 guest，二选一：

- **方式 A（推荐，最贴真实）**：让被烘焙的 rootfs 里 `guest agent` 监听 vsock，测试脚本通过宿主机 vsock 客户端发命令。这正好顺带验证了你 `guest agent` 的命令通道。
- **方式 B（临时）**：在测试镜像里放一个 `boot` 时自检脚本，沙箱起来后自动执行“解析域名 + ping + ssh 靶机”，把结果写到一个 `guest→host` 共享的卷文件里，宿主机读该文件判定。无需任何交互通道，最省事，适合 MVP 起步。

> 下面脚本以方式 B 实现（零额外依赖）。

---

### 4.3 测试镜像内置自检脚本 `selfcheck.sh`（烘焙进 T2 专用 rootfs）

```bash
#!/bin/sh
# 沙箱内 boot 时自动运行，结果写到挂载进来的 /report/result.txt
OUT=/report/result.txt

{
  echo "=== sandbox selfcheck $(date) ==="
  echo "[ip]"; ip addr show | grep 'inet ' | grep -v 127.0.0.1
  echo "[route]"; ip route | grep default
  echo "[dns] <equation>{$EXT_TARGET_DOMAIN}"; nslookup "$EXT_TARGET_DOMAIN" 2>/dev/null | tail -2
  echo "[ping]"; ping -c3 -W2 "$EXT_TARGET_IP" 2>&1 | tail -2
  echo "[ssh]"; ssh -o StrictHostKeyChecking=no -o ConnectTimeout=5 \
    -i /report/id_test "test@${EXT_TARGET_IP}" 'echo SANDBOX_OK' 2>&1
  echo "=== done ==="
} > "$OUT" 2>&1
sync
```

> **说明**：
> - `EXT_TARGET_IP / EXT_TARGET_DOMAIN` 通过 Pod 的 env 注入（在 `ContainerConfig.envs`）；
> - `/report` 是一个 host 目录通过 mount 透传给 guest（对应 runtime 的 mounts 落地）；
> - `id_test` 是测试私钥，提前烘焙或挂载。

### 4.4 T2 Pod 模板 `pod-pool/t2-lite.yaml`（在 lite 基础上加 env + report 挂载）

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: sb-t2-__ID__
  annotations:
    agent-sandbox/type: "lite"
spec:
  restartPolicy: Never
  runtimeClassName: agent-firecracker
  containers:
    - name: workload
      image: "agent-sandbox/lite-t2:1.0"   # 内置 selfcheck.sh 并设为启动执行
      env:
        - { name: EXT_TARGET_IP, value: "10.0.0.250" }
        - { name: EXT_TARGET_DOMAIN, value: "registry.test.local" }
      resources:
        requests: { cpu: "1", memory: "1Gi" }
        limits:   { cpu: "1", memory: "1Gi" }
      volumeMounts:
        - { name: report, mountPath: /report }
  volumes:
    - name: report
      hostPath:
        path: /home/USER/agent-rt-test/report/t2
        type: DirectoryOrCreate
```

### 4.5 测试脚本 `t2_availability.sh`

```bash
#!/usr/bin/env bash
set -uo pipefail
source "$(dirname "$0")/env.sh"

REPORT="$WORK/report/t2"; mkdir -p "$REPORT"; rm -f "$REPORT/result.txt"

# 1) 起靶机 sshd（若未起）：另一台/本机 namespace，IP=$EXT_TARGET_IP，放好 test 公钥
# （此处假设靶机已就绪）

# 2) 投放沙箱
sed "s/__ID__/run/" "$POOL_DIR/t2-lite.yaml" > "$MANIFEST_DIR/t2.yaml"

# 3) 等沙箱自检结果落盘（最多 40s）
ok=0
for i in $(seq 1 40); do
  [ -f "$REPORT/result.txt" ] && grep -q "=== done ===" "$REPORT/result.txt" && { ok=1; break; }
  sleep 1
done

[ $ok -eq 1 ] || { echo "T2 FAIL: no selfcheck report"; rm -f "$MANIFEST_DIR/t2.yaml"; exit 1; }

echo "-------- selfcheck report --------"; cat "$REPORT/result.txt"; echo "-----------------------------"

# 4) 判据
fail=0
grep -q "inet " "$REPORT/result.txt"          || { echo "FAIL: no IP"; fail=1; }
grep -q "default" "$REPORT/result.txt"        || { echo "FAIL: no route"; fail=1; }
grep -q "0% packet loss" "$REPORT/result.txt" || { echo "FAIL: ping"; fail=1; }
grep -q "SANDBOX_OK" "$REPORT/result.txt"     || { echo "FAIL: ssh exec"; fail=1; }

rm -f "$MANIFEST_DIR/t2.yaml"
[ $fail -eq 0 ] && { echo "T2 PASS"; exit 0; } || { echo "T2 FAIL"; exit 1; }
```

---

### 4.6 为什么这样测是对的

- 自检脚本在 **guest 内部**跑，验证的是真正的出站链路（路由 + SNAT + DNS），而非入站，契合你的产品网络模型。
- SSH 到外部靶机执行命令并拿到 `SANDBOX_OK`，等价证明“沙箱能与外部建立可用的交互式会话”——这正是 runtime 该交付的网络能力上限，隧道鉴权之上的事不掺进来。
- 结果走 host 挂载文件回流，不依赖任何尚未实现的交互通道，MVP 可立即跑。

## 五、T3 性能/压力测试 —— 冷启动耗时 + 单机密度

### 5.1 命题与判据

**命题 A（启动性能）**：单 VM 从“投放”到“Running”的耗时分布（p50/p90/p99）在目标阈值内。  
**命题 B（密度）**：单机并发拉起到第 N 个时仍稳定（无失败、无 OOM、无误驱逐、控制面不崩），记录最大稳定并发数。

| 指标           | 采集方式                                                                 |
|----------------|--------------------------------------------------------------------------|
| 单 VM 冷启动耗时 | 投放时间戳 ↔ `crictl inspectp` 中 `created_at` / `READY` 时间戳 之差       |
| 并发启动成功率   | 成功 READY 数 / 投放数                                                   |
| 密度上限         | 持续加压直到首次出现失败/OOM/驱逐，记录前一个稳定档                         |
| 资源水位         | 每秒采 `free`、`pgrep -c firecracker`、`fd` 数、`cgroup` 数                |

---

### 5.2 必须制造并发（否则结论无效）

standalone kubelet 串行处理 manifest 变更，单纯多丢 yaml 不能真并发。两个手段：

- **真并发投放**：用 `crictl runp` 直接并发打 `RunPodSandbox`（绕过 kubelet 串行），专测 runtime 的并发能力（锁、VM 创建风暴）。
- **模拟并发**：通过 `kubectl create -f` 批量提交多个 Pod YAML，配合 `--burst` 参数或 client-side 并发控制（需注意 API server 限流）。

> ⚠️ 注意：T3 必须在 T2 通过后执行，避免基础连通性问题干扰性能归因。

#### **5.3 启动耗时脚本 `t3_latency.sh`（经 crictl 并发，纯测 runtime）**

```bash
#!/usr/bin/env bash
set -uo pipefail
source "$(dirname "$0")/env.sh"

N=${1:-50}          # 并发起 N 个
CONC=${2:-10}       # 并发度

CSV="$RESULT_DIR/t3_latency.csv"; echo "id,start_ms,ready_ms,latency_ms,result" > "$CSV"

mk_podjson() {  # 生成 crictl runp 用的 pod.json
  cat > "/tmp/pod-$1.json" <<EOF
{
  "metadata": {"name":"perf-$1","namespace":"default","uid":"uid-$1","attempt":0},
  "annotations": {"agent-sandbox/type":"lite"}, "linux": {}
}
EOF
}

launch_one() {
  local id=$1; mk_podjson "$id"
  local t0=$(date +%s%3N)
  local pid=$(CRICCTL runp "/tmp/pod-$id.json" 2>/dev/null)
  local res="FAIL"; t1=$t0
  if [ -n "$pid" ]; then
    for i in $(seq 1 100); do   # 最多等 10s
      $CRICCTL inspect "$pid" 2>/dev/null | grep -q SANDBOX_READY && { res="OK"; break; }
      sleep 0.1
    done
    t1=$(date +%s%3N)
    [ "$res" = "OK" ] && $CRICCTL stopp "$pid" >/dev/null 2>&1 && $CRICCTL rmp "$pid" >/dev/null
    fi
  echo "$id,$t0,<equation>t1,<equation>((t1-t0)),$res" >> "$CSV"
}

# 并发池
running=0
for id in $(seq 1 "$N"); do
  launch_one "$id" &
  running=$((running+1))
  [ $((running % CONC)) -eq 0 ] && wait
done
wait

# 统计
echo "=== latency summary (ms) ==="
awk -F, 'NR>1 && $5=="OK"{print $4}' "$CSV" | sort -n | awk '
{
  a[NR]=$1; END {
    n=NR; if(n==0){print "no success"; exit}
    print "count="n;
    print "p50="a[int(n*0.5)];
    print "p90="a[int(n*0.9)];
    print "p99="a[int(n*0.99)?int(n*0.99):n];
    print "max="a[n]'
' "$CSV"
echo "success=$(awk -F, '$5=="OK"' "$CSV" | wc -l)/$N"
```

#### **5.4 密度阶梯脚本 `t3_density.sh`（经 kubelet，测稳态密度）**

```bash
#!/usr/bin/env bash

set -uo pipefail
source "$(dirname "$0")/env.sh"

STEPS=(10 30 50 60 120)        # 密度阶梯，按机器规格调
MON="$RESULT_DIR/t3_density_monitor.csv"
echo "ts,target,fc_procs,mem_used_mb,mem_avail_mb,evict_cnt" > "$MON"

monitor() {  # 后台每秒采水位
    while :; do
        local fc=$(pgrep -c firecracker 2>/dev/null || echo 0)
        local mu=$(free -m | awk '/^Mem:/{print $3}')
        local ma=$(free -m | awk '/^Mem:/{print $7}')
        local ev=$(grep -ci "evict\|DiskPressure\|OOM" "$LOG_DIR/kubelet.log")
        echo "$(date +%s),${CUR},${fc},${mu},${ma},${ev}" >> "$MON"
        sleep 1
    done
}

CUR=0; monitor & MON_PID=$!

prev=0
for target in "${STEPS[@]}"; do
    CUR=$target
    echo "=== ramp to $target VMs ==="
    for id in $(seq $((prev+1)) "$target"); do
        sed "s/__ID__/$id/" "$POOL_DIR/lite.yaml" > "$MANIFEST_DIR/lite-id.yaml"
    done
    prev=$target

    # 等待该档全部 READY，最多 60s
    ok=0
    for i in $(seq 1 60); do
        ready=$(kubectl pods -q --state ready 2>/dev/null | wc -l)
        [ "$ready" -ge "$target" ] && { ok=1; break; }
        sleep 1
    done

    ready=$(kubectl pods -q --state ready 2>/dev/null | wc -l)
    evict=$(grep -ci "evict\|OOM" "$LOG_DIR/kubelet.log")
    echo "target=$target ready=$ready evict=$evict"
    if [ $ok -ne 1 ] || [ "$evict" -gt 0 ]; then
        echo ">>> density ceiling around $prev (failed at $target)"; break
    fi

    sleep 15   # 该档稳态观察
done

# 清理
rm -f "$MANIFEST_DIR/lite-*.yaml"
kill "$MON_PID" 2>/dev/null
echo "monitor data -> $MON"
```

### 5.5 为什么这样测是对的

- 耗时测量用两个独立时间戳（投放时刻 vs `crictl` 观测到 READY），不依赖 runtime 自报，口径客观；`crictl runp` 直连绕过 kubelet 串行，纯测 runtime 并发能力。
- 密度用阶梯加压 + 每秒水位采样，能定位“第一个崩点”而不是只给个数字；同时抓 OOM/驱逐，把“塞进去了”和“塞进去还稳”区分开。
- 密度瓶颈本就发生在单机内部，`standalone` 测得真实；多节点只是线性叠加，不必在 MVP 引入。
- 注意：若你已上 snapshot/restore，T3 的 p50 应进入百毫秒级；若还没上，这个测试正好给出“裸 boot 基线”，量化 snapshot 之后的收益。

### 八、两个实现侧提醒（影响测试能否跑起来）
