# only-agent-sandbox Runtime 设计文档

**版本**：MVP v0.1  
**语言**：Rust  
**目标**：在 Firecracker microVM 之上实现最小 CRI runtime，对接 K8s/K3s，支持 snapshot 高速恢复 + 高密度部署。
注意，这一份概要设计是粗略的，尚未完成的，可以改动的

---

## 0. 文档范围与设计目标

| 维度   | 目标 |
|--------|------|
| **功能** | 实现 CRI 最小集 (`RuntimeService` 14 + `ImageService` 4)，让 kubelet 能正常起停 Pod |
| **启动** | 沙箱通过 Firecracker snapshot 恢复，亚秒级拉起 |
| **隔离** | 每 VM 独立 Linux netns; rootfs 只读 ext4；按 `type` 挂可写 ext4 / 云盘 |
| **约束** | 沙箱类型 ≤ 10 (MVP 3 种, id 0-2)；不拉起任意容器；镜像预烘焙白名单 |
| **性能** | PLEG 每秒查询走本地 store, O(1) 读；写路径才触原语 |

> **非目标 (MVP 明确不做)**: `Exec`/`Attach`/`PortForward`、在线资源热调、CRI 日志、`ContainerStats`、真正对接 CRI 网络插件（但预留 netns）。

| 8    | CreateContainer      | Runtime  | 建容器         | 真实实现                         |

| 10   | StopContainer        | Runtime  | 停容器         | 真实实现                         |
| 11   | RemoveContainer      | Runtime  | 删容器         | 真实实现 (幂等)                  |

## 1. 总体架构

### 1.1 三层职责

```plaintext
kubelet — unix:///run/oas.sock →
│
├─ ① API / CRI 层 (oas-cri)
│    纯翻译: proto ⇄ 内部模型；幂等短路；错误→Status
│    不持有业务状态，不直接碰 syscall
│
├─ ② 编排层 (oas-manager) ← 业务大脑，连接上下三层
│    状态机 + 幂等键 + ID 分配 + 后台 reconcile
│
└─ ③ a Firecracker   │ ③ b 网络        │ ③ c 存储         │ Store
     (oas-driver)    │ (oas-net)       │ (oas-storage)    │ (oas-store)
     4 原语 + FD      │ netns/tap/IPAM  │ rw-ext4/云盘     │ redb 持久化
                      │                 │                  │ 5 张表
│
└─ 带外 agent 通道（回灌 exit_code/finished_at）→ Store
```

### 1.2 核心设计决策（贯穿全文）

1. **薄翻译 + 单一事实源**：CRI 层无状态，所有状态在 store；`List*` / `*Status` 只读 store。
2. **声明态 vs 实际态分离**：store 是声明态，Firecracker `list_vm/get_vm` 是实际态，后台 reconcile 周期对账。
3. **双层幂等**：API 层以 K8s 身份（`pod_uid` / `sandbox_id+name+attempt`）幂等；driver 层 `create_vm` 原子幂等。
4. **trait 化下层**：`driver/net/storage/store` 全部 trait 暴露，manager 持 trait object → 可注入 mock；CRI 未通时先跑状态机。
5. **netns 隔离线程**：所有进 netns 的 syscall 关进 `spawn_blocking` 专用线程，主 async 路径不碰 netns。

## 2. 层间接口（契约定义）

> 接口是本设计的骨架，先定契约再讲实现。所有接口用 `trait + \`async_trait\`` 表达。

### 2.1 编排层 → Firecracker 原语层

```rust
#[async_trait]
pub trait FirecrackerDriver: Send + Sync {
    // 原子幂等。type_id 决定 vCPU/mem/rootfs/drive 拓扑；
    // spec 把 per-VM 可写层/云盘 PATCH 进 snapshot 预留的 drive slot；
    // 完成时写 event_fd 通知。
    async fn create_vm(&self, netns_path: &str, type_id: u8,
                       spec: VmSpec, event_fd: RawFd) -> Result;

    async fn get_vm(&self, id: VmId) -> Result;
    // 幂等：删不存在返回 Ok；不保证立即停止，调用方轮询 get_vm 到 Stopped。
    async fn delete_vm(&self, id: VmId) -> Result<(), DriverError>;

    async fn list_vm(&self) -> Result, DriverError>;
}
```
> **回收边界约定**：VM 进程由本层回收；netns/ext4/IP 租约由编排层调网络、存储层回收，职责不重叠。

### 2.2 编排层 → 网络层

```rust
#[async_trait]
pub trait NetworkManager: Send + Sync {
    // 建 netns + tap + 配 IP/路由/NAT，返回网络上下文（供 snapshot 克隆确定性重建）。
    async fn setup(&self, sandbox_id: &str) -> Result;
    // 幂等回收 netns / tap / 释放 IP 租约。
    async fn teardown(&self, net: &NetConfig) -> Result<(), NetError>;
}
```

### 2.3 编排层 → 存储层

```rust
#[async_trait]
pub trait StorageManager: Send + Sync {
    // 按 type 制备每 VM 可写 ext4(COW/overlay)，解析 annotation 里的云盘设备。
    async fn provision(&self, sandbox_id: &str, type_id: u8,
                       cloud_disk_ref: Option<&str>) -> Result;
    // 幂等清理可写层文件、解绑云盘。
    async fn cleanup(&self, disk: &DiskConfig) -> Result<(), StorageError>;
}
```

### 2.4 编排层 → 持久化层

```rust
pub trait Store: Send + Sync {
    fn put_sandbox(&self, r: &SandboxRecord) -> Result<(), StoreError>;
    fn get_sandbox(&self, id: &str) -> Result, StoreError>;
    fn get_sandbox_by_uid(&self, pod_uid: &str) -> Result, StoreError>;
    fn list_sandboxess(&self, filter: &SandboxFilter) -> Result, StoreError>;
    fn delete_sandbox(&self, id: &str) -> Result<(), StoreError>;
    // container 同构 ...
    // IPAM 租约原子分配（崩溃后不重复分配）。
    fn lease_ip(&self, cidr: &str) -> Result;
    fn release_ip(&self, lease: &IpLease) -> Result<(), StoreError>;
    // 单事务执行（建资源+落库的原子点）。
    fn transaction(&self, f: F) -> Result
        where F: FnOnce(&mut Txn) -> Result;
}
```

> **依赖方向**：`oas-cri → oas-manager → {driver, net, storage, store}`，全部单向，无环。`manager` 是唯一同时握住四个 trait 的地方。

## 3. 各层详述

### 3.1 ① API / CRI 层 (oas-cri)

**职责**：实现 tonic 生成的 `RuntimeService` / `ImageService` trait，做三件事——proto ⇄ model 转换、幂等短路、把领域错误翻译成 `tonic::Status`。不写业务逻辑，全部委托给 manager。

#### 关键模块：

| 文件                | 内容 |
|---------------------|------|
| `runtime_svc.rs`    | 14 个 RuntimeService 方法，每个 ≤ 20 行：转换 → 调 manager → 转换回 |
| `image_svc.rs`      | 4 个 ImageService 方法，白名单校验 + 假 fsinfo |
| `convert.rs`        | 全链路原样透传：metadata/labels/annotations 存即原样、取即原样 |
| `unsupported.rs`    | `Exec`/`Attach`/`PortForward`/`UpdateContainerResources` → `Status::unimplemented` |
| `error.rs`          | `impl From<OasError> for tonic::Status` 集中映射 |

#### 关键实现红线（代码层面强约束）：
- `convert.rs` 禁止用 `Default` 彻底覆盖 metadata —— 这是“自研 CRI 头号死法”的根因。
- 幂等方法（`Stop*` / `Remove*`）删不存在 → 在 `error.rs` 统一吞成 `Ok`，不让任何 handler 漏。
- `Status` 写死两条 `condition=true`；`ImageFsInfo` 返回 "磁盘很空" 假值。

#### 错误映射示例：

```rust
impl From for tonic::Status {
    fn from(e: OasError) -> Self {
        match e {
            OasError::NotFound(_) => Status::not_found(e.to_string()),
            OasError::ImageNotInList(_) => Status::not_found(e.to_string()),
            OasError::TypeMismatch(_) => Status::invalid_argument(e.to_string()),
            _ => Status::internal(e.to_string()),
        }
    }
}
```

### 3.2 ② 编排层 (oas-manager)

**职责**：业务大脑。生命周期编排、两个状态机、幂等判定、ID 分配、后台 reconcile。

#### 关键类：

```rust
pub struct Manager {
    driver: Arc,
    net:    Arc,
    storage: Arc,
    store:  Arc,
    types:  SandboxTypeTable,        // // type_id 0-2 → 配置
    locks:  PerKeyLock,      // // per-sandbox 串行化，防并发重建
}
```

#### SandboxType 表（配置中枢，与 YAML 对齐）：

```rust
pub struct SandboxType {
    pub type_id: u8,
    pub vcpu: u32, pub mem_mib: u32,
    pub snapshot_path: String,      // // 该 type 的 base snapshot
    pub rootfs_ro: String,          // // 只读 rootfs.ext4
    pub has_rw_layer: bool,         // // type1/2 = true
    pub has_cloud_disk: bool,       // // type2 = true
    pub image_whitelist: Vec, // // 与 spec.containers[].image 对齐
}
```

| type_id | vCPU/Mem | 只读 rootfs | 可写 ext4 | 云盘       | image   |
|---------|----------|-------------|-----------|------------|---------|
| 0       | 1c/512M  | base-0      | —         | —          | img-a   |
| 1       | 2c/2G    | base-1      | ✓         | —          | img-b   |
| 2       | 4c/8G    | base-2      | ✓         | ✓ (Pod 注入) | img-c   |

#### 两个状态机：

**Sandbox FSM**（映射 `PodSandboxStatus.state`）：
```plaintext
RunPodSandbox: net.setup → storage.provision → driver.create_vm(event_fd) → 等就绪
 ├ 成功 → SANDBOX_READY （写 vm_id/pod_ip/created_at）
 └ 失败 → NOTREADY （留痕, kubelet 重建）

READY → StopPodSandbox → driver.delete_vm + 轮询Stopped + net.teardown → NOTREADY
NOTREADY → RemovePodSandbox → storage.cleanup + 删记录（幂等）
reconcile 发现 VM 没了 → 置 NOTREADY
```

**Container FSM**（映射 `ContainerStatus.state`，字段最严）：
```plaintext
CreateContainer → CREATED （校验 image 白名单 + resources/type 一致性 + 落库）
 └ StartContainer → (带外 agent 在 guest 拉起进程) → RUNNING (started_at)
    ├ 进程退出，agent 回灌 → EXITED (exit_code/finished_at/reason)
    ├ StopContainer: SIGTERM→等timeout→SIGKILL → EXITED
    └ VM 失联(reconcile) → UNKNOWN
EXITED/UNKNOWN → RemoveContainer → 删记录（幂等）
```

#### reconcile loop（独立 tokio task）：

```plaintext
启动/周期：
  vms = driver.list_vm()
  对 store 中每条 sandbox:
    VM 不存在 → 置 NOTREADY/EXITED（触发重建）
    VM 存在 → driver.get_vm 刷新 state(Degraded→NOTREADY)
  对 vms 中 store 无记录的（孤儿）→ driver.delete_vm 回收
```
> **作用**：崩溃恢复、孤儿回收、让 PLEG 读到的声明态持续新鲜。

### 3.3 ③a Firecracker 原语层 (oas-driver)

**职责**：把 4 原语落到 Firecracker HTTP (UDS) 调用，屏蔽 snapshot/drive 细节。

#### 关键数据结构：

```rust
pub struct VmId(pub u64);

pub enum VmLifecycle {
    Creating, Restoring, Running, Degraded, Stopping, Stopped,
}

pub struct VmStatus {
    pub started: bool,
    pub healthy: bool,
    pub lifecycle: VmLifecycle,
}

pub struct VmSpec {
    pub rw_layer_path: Option,   // // per-VM 可写 ext4
    pub cloud_disk_dev: Option,  // // per-VM 云盘块设备
}
```

#### `create_vm` 内部流程 (MVP = snapshot restore)：

1. 校验幂等：同 `(type_id, netns)` 已在建 → 返回旧 `VmId`
2. 启动 jailer —— netns `<netns_path>`（在子进程 setns，本进程线程不动）
3. `PUT /snapshot/load` ← 加载 type 的 base snapshot
4. `PATCH /drives` ← 把 `spec.rw_layer_path / cloud_disk_dev` 写进预留 slot  
   （drive slot 数量在制版期已固定，运行期只能替换后端文件）
5. `PATCH /vm {state: Resumed}`
6. 健康探测就绪 → `write(event_fd)` → 返回 `VmId`

> **eventfd 异步等待**：`nix::sys::eventfd` 建 fd → `tokio::io::unix::AsyncFd` 包装 → `readable().await`，不 busy-poll。  
> **delete_vm 轮询**：`tokio::time::interval` 周期 `get_vm` 到 `Stopped` 或不存在。

#### 关键决策：
> MVP 只用 `snapshot/load` + `PATCH drives` + `PATCH vm` 三个 Firecracker API，自建薄 UDS client (hyper) 即可，不强依赖第三方 SDK，依赖更少更可控。

### 3.4 ③b 网络层 (oas-net) —— Rust 唯一硬骨头

**职责**：为每 VM 建 netns + tap + IP / 路由 / NAT，确保 snapshot 克隆的网络可确定性重建。

#### 关键数据结构：

```rust
pub struct NetConfig {
    pub netns_path: String,   // // /var/run/netns/oas-
    pub tap_name: String,     // // 克隆间保持一致，让 guest 无感
    pub mac: String,
    pub pod_ip: String,
    pub gateway: String,
    pub lease: IpLease,
}
```

#### 核心：netns × tokio 线程亲和性处理
> 所有进 netns 的 syscall 关进 `spawn_blocking` 专用线程，用 RAIL guard 保证 setns 一定还原：

```rust
struct NetnsGuard { host_fd: OwnedFd } // // 进入时保存 host netns fd
impl NetnsGuard {
    fn enter(path: &str) -> Result {
        let host = open("/proc/self/ns/net")?; // // 记住来源
        let target = open(path)?;             // // 钻进目标 netns
        setns(target, CLONE_NEWNET)?;
        Ok(Self { host_fd: host })
    }
}
impl Drop for NetnsGuard {
    fn drop(&mut self) { let _ = setns(&self.host_fd, CLONE_NEWNET); } // // 出错也还原
}

// 整套网络配置打包成同步闭包，绝不跨 .await
async fn setup_in_netns(path: String, cfg: TapPlan) -> Result<(), NetError> {
    tokio::task::spawn_blocking(move || {
        let _g = NetnsGuard::enter(&path)?;   // // 进入
        create_tap(&cfg.tap)?;                // // 一气呵成
        assign_ip(&cfg.tap, &cfg.ip)?;
        add_routes(&cfg.routes)?;
        Ok(())
    }).await?
}
```

> **能不能 setns 就不 setns**？tap 可先在 host 建好，用 netlink `set link netns <fd>` 通过 fd 引用移进目标 netns；只有 “给 netns 内网卡配 IP / 路由” 绕不开。才走上面的专用线程。

### 3.5 ③c 存储层 (oas-storage)

**职责**：按 `type` 制备每 VM 可写 ext4、绑定云盘、清理。

#### 关键数据结构：

```rust
pub struct DiskConfig {
    pub rw_layer_path: Option,  // // /var/lib/oas/rw/.ext4
    pub cloud_disk_dev: Option, // // /dev/xxx，来自 annotation
}
```

#### 制备策略：
- 可写 ext4 用 COW/overlay over base（reflink 或 qcow 式 backing），避免每 VM 全量拷贝，这是高密度的关键。
- 云盘是本地块设备直通，storage 层只做“解析 annotation 里的设备引用 + 校验存在”，不格式化。

---

### 3.6 持久化层 (oas-store) —— redb 5 张表

| 表           | key               | 关键字段 |
|--------------|-------------------|----------|
| `sandbox`    | `sandbox_id`      | `pod_uid` (★幂等键)、`metadata/labels/anno` (★原样)、`type_id`, `vm_id`, `netns/tap/mac`, `pod_ip`, `rw_layer/cloud_disk`, `state`, `created_at` |
| `container`  | `container_id`    | `sandbox_id`、`metadata`(★)、`image/ref`、`command/args/env/mounts/resources/state`、`created/started/finished_at`、`exit_code/reason/message`(★带外回灌)、`labels/anno` |
| `ipam`       | `ip`              | 租约 (★崩溃后不重复分配) |
| `image`      | `image`           | 白名单缓存 (可选，主要来自 config) |
| `meta`       | `key`             | schema 版本、`UpdateRuntimeConfig` 下发的 `podCIDR` |

> **事务边界 = 幂等与恢复的原子点**：`RunPodSandbox` 里“建 VM 成功 → 写最终态”放进一个 redb `WriteTransaction` 提交。若在“建了 VM 还没 commit”间崩溃，reconcile 用 `list_vm + store` 反查孤儿回收。

> `SandboxRecord` / `ContainerRecord` 完整结构见上一轮 `derive(Serialize, Deserialize)` 定义，此处不重复

## 5. 使用到的设计模式

| 模式                  | 应用位置                     | 解决什么 |
|-----------------------|------------------------------|----------|
| **Adapter (适配器)**  | `oas-cri` 整层               | 把 K8s CRI proto 适配到内部领域模型，kubelet 与业务解耦 |
| **Facade (外观)**     | `Manager`                    | 对 CRI 层提供统一编排入口，屏蔽下面四个子系统 |
| **Strategy (策略) + Registry** | `SandboxTypeTable`       | `type_id` 0-2 选择不同 vCPU/rootfs/盘拓扑，新增 `type` 只加表项 |
| **Dependency Injection** | `main.rs` 注入 trait object | 下层可换 mock，CRI 未通时先跑状态机 |
| **State Machine**     | `sandbox_fsm/container_fsm`  | 把 PLEG 每秒 diff 的状态流转显式化，避免重建死循环 |
| **Repository**        | `Store` trait                | 业务逻辑与 redb 存储解耦，事务边界清晰 |
| **RAII Guard**        | `NetnsGuard`                 | setns 必还原，异常路径也不污染线程 |
| **Reconciliation Loop** | `reconcile.rs`             | 声明态 / 实际态对账，崩溃恢复 + 孤儿回收 (K8s 控制器范式) |
| **Idempotency Key**   | `pod_uid / sandbox_id+name+attempt` | kubelet 重试不产生重复 VM |
| **Object Pool (思想)** | snapshot 克隆 + COW ext4    | 高密度下复用 base，避免全量拷贝 |

---

## 6. 三条实现红线（收口）

1. **metadata + labels 全链路原样**  
   → `convert.rs` 存即原样、取即原样，禁 `Default` 覆盖。  
   *这是“自研 CRI 头号死法”的根因。*

2. **exit_code 带外 agent 回灌**  
   → driver 的 `VmStatus` 推断不出进程退出码。  
   *必须由 agent 主动上报 `exit_code`，否则 `restartPolicy: OnFailure` 无法触发。*

3. **`List*` / `*Status` 只读 redb，不打 Firecracker**  
   → 实际态由 reconcile 异步刷新；`ImageFsInfo` 假返回 "磁盘很空"；`Status` 写死两条 `condition=true`。

> **字段最终以目标 K8s/K3s 版本的 `runtime.v1 api.proto` 为准，实现前对一遍。**

> 这份文档可以直接作为开发基线。需要的话可以再往下细化两个方向之一：  
> (a) 把它整理成一份飞书文档便于团队协作评审；  
> (b) 直接产出可编译的 workspace 骨架代码（各 crate 的 `Cargo.toml` + trait 定义 + 空实现 + mock driver），让你 `cargo build` 通过后就能先把 PLEG 状态机联调起来。你定方向。

## §7 带外 Agent 协议契约 (PO)

> 这是当前最大的隐性依赖。文档多处写 “带外 agent 回灌 exit_code”“guest 内拉起进程”，但从没定义这个 agent 是什么、怎么通信。它实际上是 runtime 的第二条控制平面，**必须像 CRI 一样郑重定义**。

### 7.1 传输层选型：vsock（而非网络隧道）

**控制平面**（起停进程、回灌状态）建议走 Firecracker 原生 `virtio-vsock`，不要和你的 SSH 业务隧道混用：

- ✅ `vsock` 不依赖 netns/IP/host 用 `(CID, port)` 直连 guest，网络没配好也能通，适合做控制带。
- ✅ 每 VM 分配唯一 CID, host 侧 connect。
- ⚠️ **坑**：vsock 连接状态会被 snapshot 固化，恢复后旧连接失效。  
  **约定**：guest agent 在每次 resume 后主动重连 host, host 侧 vsock 监听是长存的。

> SSH / 业务 exec 仍走你原定的注册中心隧道；**控制平面单独走 vsock，两者解耦**。

---

## 7.3 可靠性约定（必须写进 FSM）

| 场景                                 | runtime 行为 |
|--------------------------------------|--------------|
| agent 在超时内没 `Hello`             | sandbox 标 `Degraded` → `NOTREADY`；container 停在 `CREATED` |
| `StartProcess` 已发但没收到 `Started` | 按超时重发（agent 侧 `container_id` 幂等，已起则回 `already-running`） |
| host 进程重启，丢了 vsock 连接       | 依赖 guest 主动重连 + `Hello` 重新认领；reconcile 据此补状态 |
| agent 始终不可达但 VM healthy        | container → `UNKNOWN`，不能谎报 `RUNNING` |

> **红线**：`exit_code` 只有 `Exited` 消息能给。收不到就是 `UNKNOWN`，严禁用 `"VM 还活着"` 反推成 `exit_code=0` —— 否则 `restartPolicy: OnFailure` 直接失效。

---

## §8 Snapshot 烘焙规范 + drive slot 预留 (PO)

> `create_vm` 在 §3.3 里写了 “PUT /snapshot/load + PATCH /drives”，但这些 snapshot 怎么来、slot 怎么预留没定义。这是离线制版流程，得单列。

### 8.1 每 type 一条烘焙流水线

```plaintext
1. 冷启一个 builder VM:
   - boot kernel + rootfs_ro (只读)
   - PUT /drives 声明【全部】drive slot (关键):
        drive_id="rootfs"    ro=true   path=base-N.ext4
        drive_id="writable"  ro=false  path=<占位空 ext4>   (type1/2 才声明)
        drive_id="clouddisk" ro=false  path=<占位>          (type2 才声明)
   - 配置 vsock device、(可选)MMDS —— *这些必须在 snapshot 前配好，恢复期不能新增设备*
2. 装入 guest agent，启动它，等到“业务就绪点”（agent Hello 通）
3. PATCH /vm {state: Paused}
4. PUT /snapshot/create → 产出 {mem_file, vmstate_file}
5. 落盘 + 记录元数据（见 8.3），打 checksum
```

> **核心铁律**：drive 的 slot 数量在制版期定死，运行期只能 `PATCH /drives` 换 slot 后端文件路径，**不能加 slot**。所以 type 的盘拓扑（有没有 writable、有没有 clouddisk）在烘焙时就固化 —— 这正好对你 `type ↔ 对应固定拓扑` 的设计。

### 8.2 恢复期 `create_vm` 的 PATCH 映射

```plaintext
load(base-N) →
  PATCH drive "writable"  → per-VM 新建的 rw ext4 路径
  PATCH drive "clouddisk" → 该 Pod 注解指定的云盘块设备
  PATCH vm {state: Resumed}
```

### 8.3 Snapshot 版本与兼容性（否则会神秘崩）

> snapshot 不跨 Firecracker 版本、不跨内核移植。元数据必须记并在 load 前校验：

```rust
pub struct SnapshotMeta {
    pub type_id: u8,
    pub fc_version: String,      // // 必须与运行时 FC 版本一致
    pub kernel_version: String,
    pub drive_slots: Vec, // // slot 拓扑，供 create_vm 校验 PATCH 目标存在
    pub vsock_cid_base: u32,         // // 用于生成 per-VM CID
    pub checksum: String,
}
```

> **load 前 `fc_version` 不匹配 → 直接拒绝并报清晰错误**，别让它在 guest 里以诡异方式崩。

## §9 Pod 注解契约表 (PO)

> `type_id`、云盘引用都从 YAML 进来，这是 K8s ⇄ runtime 的正式接口，必须冻结成表，API 层据此解析：

| 来源字段                     | 注解 / 字段 key                   | 含义                     | 必填 | 校验 |
|------------------------------|-----------------------------------|--------------------------|------|------|
| `metadata.annotations`       | `agent-sandbox/type`              | `type_id` (0-2)          | 是   | 在 `type` 表内 |
| `spec.containers[].image`    | `image`                           | 工作镜像                 | 是   | 命中该 `type` 的 `image_whitelist` |
| `metadata.annotations`       | `agent-sandbox/cloud-disk`        | `type2` 的云盘块设备引用 | `type2` 必填 | 设备存在、未被占用 |
| `metadata.annotations`       | `agent-sandbox/rw-size`           | 可写层大小               | 否   | 默认值兜底 |
| `linux.resources`            | `cpu/mem`                         | 资源                     | 是   | 与 `type` 表一致性校验 |

> **一致性校验是红线**：`type` 决定的 vCPU/mem 是事实源（boot 期定死），如果 Pod spec 的 limits 与 `type` 不符，**拒绝创建**——而不是迁就——否则高密度场景必 OOM。这条要写进 `CreateContainer` 的校验逻辑。

## §10 并发模型与竞态处理 (PO)

> `PerKeyLock` 只在 §3.2 出现了类型名，但并发正确性需要明确规则，否则 PLEG 每秒并发 + reconcile 会生产脏状态。

### 10.1 锁规则

- **锁粒度**：per-`sandbox_id`（同一 Pod 的所有写串行；不同 Pod 并行）。
- **锁顺序**：固定 `sandbox_id` 锁 → `container_id` 锁，杜绝死锁。
- **读路径不加业务锁**：`List*` / `*Status` 只读 store，靠 redb 事务的 MVCC / 快照一致性，绝不等写锁（保证 PLEG 不被阻塞）。

### 10.2 必须显式处理的 4 个竞态

| 竞态                          | 处理 |
|-------------------------------|------|
| `RunPodSandbox` 在途，`StopPodSandbox` 到达 | Stop 拿同一把锁排队；若 sandbox 记录还没落库，Stop 走 "删不存在 = Ok" 幂等 |
| reconcile 改 state 与 CRI 写 state 撞 | 都走 store 事务 + per-sandbox 锁；reconcile 只在拿到锁后改，且只做收敛性修正（VM 没了才降级），不与正在进行的创建抢 |
| 同 `pod_uid` 并发两次 `RunPodSandbox`（kubelet 重试） | `get_sandbox_by_uid` 命中且健康 → 直接返回旧 id，不建第二个 VM |
| `create_vm` 成功但 commit 前崩溃 | 事务未提交 → store 无记录 → reconcile 发现孤儿 VM → `delete_vm` 回收 |

## §11 冷启动 / 进程重启恢复 (PO)

> runtime 进程自身是会重启的（升级、崩溃），恢复流程要独立成节，不能只在 reconcile 里带一句。

```plaintext
runtime 启动：
1. open redb（校验 schema 版本，见 §15）
2. 重建内存索引：pod_uid→sandbox_id, sandbox_id→container_ids
3. 重连控制平面：对每个 READY sandbox，等待 guest agent 的 Hello 重连（§7.3）
4. 首轮 reconcile（强制全量）：
   - driver.list_vm() ∪ store → u store
     - store 有 / VM 在 → get_vm 刷新 state
     - store 有 / VM 无 → 降级，删 kubelet 重建
     - store 无 / VM 在 → 孤儿，delete_vm + 回收 netns/ext4/IP 相约
5. 标记 Status 就绪，开始 serve CRI
```

> **关键**：第 5 步之前不要 serve CRI，否则 kubelet 在状态没对齐时打进来会误判。`Status` 在恢复完成前返回 `NotReady`。

## §12 容量 / 准入 / 资源核算 (P1)

> 高密度是核心目标，但 “塞多少、怎么记账” 没写。补：

- **准入**：`RunPodSandbox` 前做节点级容量检查 —— 已分配 Σ(type.mem) + 本次 ≤ 节点可用 mem × 超分系数。超了直接拒（返回 `ResourceExhausted`），让调度器另选节点。
- **cgroup**：把 microVM（firecracker 进程）放进 `linux.cgroup_parent` 指定的 cgroup，使 K8s 节点级统计 / 限制生效；jailer 支持 cgroup 配置。
- **内存账口径**：Firecracker 的 mem 是 guest 视角；host 侧还有 page cache、snapshot mem 映射。约定按 `type.mem_mib + 固定 overhead` 估算，留经验余量。
- **IP 容量**：IPAM 的 CIDR 决定单节点 Pod 上限，需与容量上限对齐。

---

## §13 网络细节补全 (P1)

> §3.4 解决了 netns 线程问题，但还差三块：

1. **DNS 注入**：用 `PodSandboxConfig.dns_config` 写 guest 的 `/etc/resolv.conf`（对应你 “沙箱要 ping 固定域名” 的需求）。snapshot 恢复后由 agent 写入，或通过 MMDS 下发。
2. **MAC/IP 确定性生成**：克隆间 tap 名 / MAC 必须一致（让 guest 无感）。host 侧用 netns 隔离消歧。约定 MAC = 固定前缀 + `sandbox_id` 派生，保证可复算、不冲突。
3. **★Snapshot 恢复后时钟漂移**：恢复出的 guest 时钟停在制版时刻，会导致 TLS / 日志 / 令牌时间错乱
   - **约定**：guest agent 在 resume 后第一件事是校时（`clock_settime` / `chrony step`）。这是 Firecracker snapshot 的经典坑，**必须写进 agent 职责**。

## §16 安全模型 (P1 · 骨架)

> “安全隔离” 是卖点，得显式写边界：

- **jailer 强制**：每 VM 经 jailer 启动 → chroot + 独立 uid/gid + cgroup + netns，逃逸面最小。
- **seccomp**：用 Firecracker 默认 seccomp filter（限制 VMM 可用 syscall）。
- **白名单即准入**：镜像、type 双白名单，天然拒绝任意容器（对应 “不能拉起其他容器”）。
- **威胁模型一句话**：信任 host 与 runtime，不信任 guest 内负载；guest 逃逸被 jailer+seccomp+microVM 三层挡住。

|------|--------------------------|-------------------------------------------|

| CRI  | oas-cri                  | 翻译层，proto ⇄ model                     |

## 21.1 过程一：节点启动 / runtime 冷启动就绪 ★最先跑  
**目的**：runtime 进程拉起后，把声明态 (ST) 与实际态 (DRV) 对齐，再对 K 宣告就绪。**就绪前绝不 serve CRI**。  
**参与**：MGR、ST、DRV、NET、STG、AG、K

### 步骤
1. `main` 装配：ST.open(校验 schema 版本) → 注入 DRV/NET/STG → 建 MGR  
2. MGR 重建内存索引  
   `ST → [Store::list_*] → MGR` （pod_uid=sandbox_id 等）
3. 首轮强制全量 reconcile：  
   `real = DRV.list_vm()`  
   `MGR → [FirecrackerDriver::list_vm] → DRV`  
   对账 `real u ST`：  
   - 有记录/VM在 → DRV.get_vm 刷新 state  
   - 有记录/VM无 → ST 置 NOTREADY（触发 K 重建）  
   - 无记录/VM在 → 孤儿：DRV.delete_vm + NET.teardown + ST.cleanup
4. 重连控制平面：对每个 READY sandbox 等 AG 的 Hello  
   `AG → [vsock] → MGR`
5. 对齐完成 → Status 才返回 `RuntimeReady/NetworkReady=true`
6. `K ← [CRI: Version/Status/UpdateRuntimeConfig/ImageFsInfo] → CRI → MGR`

> **职责**：MGR 主导对账；DRV 提供实际态；NET/STG 回收孤儿资源；ST 是恢复基准。  
> **边界**：第 5 步前 `Status` 必须返回 `NotReady`，否则 K 在状态没对齐时打进来谋判。

---

## 21.2 过程二：创建 Pod (snapshot 恢复全链路) ★最核心  
**目的**：从 `RunPodSandbox` 到容器 RUNNING，亚秒级 snapshot 恢复 + 起业务进程。  
**参与**：K、CRI、MGR、NET、STG、DRV、FC、ST、AG

### 阶段 A：RunPodSandbox（建 microVM + 网络，返回 READY+PodIP）
1. `K → [CRI: RunPodSandbox(PodSandboxConfig)] → CRI`
2. CRI.convert 解析 annotation：agent-sandbox/type, cloud-disk($9)→ model  
   `CRI → [Manager::run_sandbox] → MGR`
3. MGR 取 per-sandbox 锁；ST.get_sandbox_by_uid 幕等检查  
   命中且健康 → 直接返回 id（短路，不建第二个 VM）
4. MGR → [NetworkManager::isetup] → NET  
   NET：建 netns → tap → ST.lease_ip 分配 IP → 配路由/MAT → 返回 NetConfig  
   `NET → [Store::lease_ip] → ST`
5. MGR → [StorageManager::provision] → STG  
   STG：COW 制备 rw-ext4 + 解析云盘设备 → 返回 DiskConfig
6. MGR → [FirecrackerDriver::create_vm(netns,type_id,vmSpec,event_fd)] → DRV  
   DRV：jailer → netns 起 FC子进程（子进程setsns）→ PUT /snapshot/load(base-N)  
   → PATCH /drives/rw/cloud 路径写入桥接 slot → PATCH /vmm(Reused)  
   → 等就绪 write(event_fd) → 返回 VmId  
   `DRV → [FC HTTP/UDS] → FC`
7. MGR 等 event_fd(asyncFd 异步) → 在【一个 ST 事务】内写 SandboxRecord(READY,pod_ip,vm_id)
8. MGR → [Store::transaction] → ST
9. `K ← [CRI: PodSandboxStatus] → 读 ST → 章 state=READY + network.ip`

### 阶段 B：CreateContainer（轻启 + 落库，不起进程）
10. `K → [CRI: CreateContainer(ContainerConfig)] → CRI → MGR`
11. MGR 校验：ImageRef 各类 resources 与 type 表【一致性校验】（不符报错，$9）
12. MGR ST 写 ContainerRecord(state=CREATED) → 返回 container_id

### 阶段 C：StartContainer（管外拉起 guest 内进程）
13. `K → [CRI: StartContainer] → CRI → MGR`
14. MGR → [vsock: StartProcess(cmd,args,env,workdir)] → AG
15. AG 在 guest 内 exec 业务进程 → 回 Started(pid,started_at)  
    `AG → [vsock] → MGR`
16. MGR ST 置 RUNNING→started_at
17. `K ← [CRI: ContainerStatus] → 读 ST → state=RUNNING`

> **职责分工一句话**：CRI 解析 + 翻译；MGR 编排 + 持锁 + 落库；NET/STG 备好网络与盘；DRV 把 snapshot 恢复成 VM；AG 在 guest 内起进程并回报；ST 是唯一落点.  
> **边界**：阶段 A 任一步失败 → MGR 回滚已建资源 (NET.teardown/STG.cleanup/DRV.delete_vm)，并置 NOTREADY，留给 K 重建；create_vm 原子幂等，K 重试不产生第二个 VM。

---

## 21.3 过程三：PLEG 稳态查询心跳 ★性能命门  
**目的**：K 每秒 relist, query 量大头。**全部走本地 ST，绝不打 DRV/FC**。  
**参与**：K、CRI、MGR、ST（DRV 不参与）

### 步骤（每 ~1s）
- `K → [CRI: ListPodSandbox(filter) / ListContainers(filter)] → CRI → MGR`
- `MGR → [Store::list_*(filter)] → ST` （按 id/label/sandbox_id 收敛）
- `K → [CRI: PodSandboxStatus(id) / ContainerStatus(id)] → 逐个`
  - `MGR → [Store::get_*] → ST` → 原样回填 metadata/labels/anno + state
- `K → [CRI: Status] → 固定两 condition=true`

> **职责**：CRI/MGR 只做 O(1) 本地读 + 原样回填；实际态新鲜度由过程六 reconcile 异步保证，读路径不阻塞、不加业务锁（redis 快照一致性）。  
> **红线**：metadata/labels 原样回填（K 靠 uid+io.kubernetes.pod.* 认领）；state/exit_code 必须真实，否则反复重建。

---

## 21.4 过程四：容器进程退出 / exit_code 回灌 ★重启策略命根  
**目的**：guest 内业务进程退出 → exit_code 准确进 ST → K 据此执行 restartPolicy。  
**参与**：AG、MGR、ST、K、CRI

### 步骤
1. guest 内业务进程退出  
2. AG 捕获 → `[vsock: Exited(container_id,exit_code,finished_at,reason)] → MGR`  
3. MGR 取锁 → ST 置 EXITED + exit_code/finished_at/reason (OOMKilled/Error/Completed)  
4. 下一轮 PLEG：K ← [CRI: ContainerStatus] → 读到 EXITED + exit_code  
5. K 按 restartPolicy 决策 (OnFailure 看 exit_code≠0)

> **职责**：AG 是 exit_code 的唯一来源；MGR 落库；CRI 如实回填.  
> **红线**：收不到 `Exited` → state=UNKNOWN，严禁用 "VM 还活着" 反推 `exit_code=0`，否则 OnFailure 失效。

---

## 21.5 过程五：删除 Pod  
**目的**：优雅停进程 → 删除容器 → 关 VM → 回收资源，全程幂等.  
**参与**：K、CRI、MGR、AG、DRV、NET、STG、ST、FC

### 步骤
1. `K → [CRI: StopContainer(id,timeout)] → MGR`  
   `MGR → [vsock: StopProcess{SIGTERM,timeout}] → AG`; 超时 MGR 兜底升级 SIGKILL  
   `AG → Exited → ST` 置 EXITED
2. `K → [CRI: RemoveContainer] → MGR → ST.delete_container(幂等)`
3. `K → [CRI: StopPodSandbox] → MGR`  
   `MGR → [FirecrackerDriver::delete_vm] → DRV` → (FC 关 VM, 不保证立即)  
   `MGR` 轮询 `[get_vm]` → 直到 Stopped/不存在  
   `MGR → [NetworkManager::teardown] → NET` （删 netns/tap + release_ip）  
   `ST` 置 sandbox NOTREADY
4. `K → [CRI: RemovePodSandbox] → MGR`  
   `MGR → [StorageManager::cleanup] → STG` （删 rw-ext4/解绑云盘）→ `ST.delete_sandbox`

> **职责**：AG 优雅停进程；DRV 关 VM 进程（回收边界：VM 归 DRV/FC）；NET/STG 回收 netns/盘/IP（归 MGR 调度）；ST 删记录.  
> **边界**：所有 Stop/Remove 幂等，删不存在返回 Ok（在 CRI error 层统一吞）。

---

## 21.6 过程六：后台 reconcile 对账 ★声明态新鲜度来源  
**目的**：周期对齐 ST（声明态）与 DRV（实际态），支撑过程三的读路径新鲜度 + 崩溃恢复 + 孤儿回收.  
**参与**：MGR（独立 tokio task）、DRV、ST、NET、STG

### 步骤（每 N 秒）
```plaintext
real = DRV.list_vm()
MGR → [list_vm] → DRV
对 ST 每条 sandbox（拿 per-sandbox 锁，仅做收敛修正）：
  VM 不存在         → ST 置 NOTREADY/EXITED（触发 K 重建）
  VM 存在 → DRV.get_vm → Degraded 映射 NOTREADY，刷新 state/health
real 中 ST 无记录（孤儿）→ DRV.delete_vm + NET.teardown + STG.cleanup
```

> **职责**：MGR 是唯一对账方；DRV 给实际态；NET/STG 执行回收.  
> **边界**：reconcile 与 CRI 写共享同一把 per-sandbox 锁；reconcile 只降级 / 回收，不与正在进行的创建抢（避免误删在途 VM）。

---

## 21.7 过程七：镜像校验（退化路径）  
**参与**：K、CRI、ST/config

### 起容器前：
- `K → [CRI: ImageStatus] → 命中白名单返回 Image，否则空`
- （空时）`K → [CRI: PullImage] → 不真拉，白名单内返回已存在 image_ref，白名单外报 error`
- `image GC: K ← [CRI: ListImages] → 返回固定白名单；RemoveImage 空操作`

> **职责**：纯白名单校验（来自 config），天然拒绝非法镜像.

---

## 21.8 过程八：驱逐防护（ImageFsInfo）  
**参与**：K（eviction manager）、CRI

### 周期：
- `K → [CRI: ImageFsInfo] → 返回 "磁盘很空" 假值 (used < capacity)`

> **职责**：这是 "非生命周期但决定节点可用性" 的方法。报真实 / 乱报都会触发误驱逐，固定返回健康假值。

## 21.9 全局协作矩阵（谁调谁 · 一图收口）

| 调用方 ↓ \ 被调 → | CRI           | MGR                     | DRV                   | NET                     | STG                   | ST          | AG             | FC               |
|-------------------|---------------|-------------------------|-----------------------|-------------------------|-------------------------|-------------|----------------|------------------|
| **K (kubelet)**   | CRI gRPC      |                         |                       |                         |                         |             |                |                  |
| **CRI**           |               | Manager API (Rust 调用) |                       |                         |                         |             |                |                  |
| **MGR**           |               |                         | FirecrackerDriver trait | NetworkManager trait    | StorageManager trait    | Store trait | vsock 协议     |                  |
| **DRV**           |               |                         |                       |                         |                         |             |                | FC HTTP/UDS      |
| **AG (回报)**     |               | vsock 协议              |                       |                         |                         |             |                |                  |

> **三类接口边界**：  
> ① 对外 = CRI gRPC（K ↔ CRI）；  
> ② 进程内 = Rust trait（MGR ↔ 下层）；  
> ③ 第二控制平面 = vsock（MGR ↔ AG）；  
> ④ 对 VMM = FC HTTP/UDS（DRV ↔ FC）。  
> **MGR 是唯一同时握住 trait 与 vsock 的枢纽**，所有跨组件协作都收敛到它。
